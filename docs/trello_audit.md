# Auditoría del repositorio frente al Trello RiTech SAS

## Actualización después de la auditoría

El propietario confirmó que el alcance es únicamente café con Flutter/Supabase. Las tarjetas de cacao y de otros stacks no aplican a esta entrega. Se implementaron los indicadores del dashboard (S4-14 a S4-18), con lotes como inventario de café, solicitudes/aceptadas y transporte separado por estados. La revisión final aprobó 63 pruebas Flutter, 34 PostgreSQL/PGlite y 28 de funciones Deno; véase [verification_20261109.md](verification_20261109.md). Se ejecutó el flujo completo contra Supabase con cuatro cuentas DEMO, seis cargas de soportes sintéticos, convenio aceptado por su titular, lote de 100 kg, aprobación, toma de carga y entrega persistida. Véanse `demo_guide.md` y `demo_backend_evidence.json`. El Pixel_9a arrancó usando el SDK correcto. La tabla inferior se conserva como **diagnóstico inicial anterior a estos cambios**, no como estado actualizado de las tarjetas ya resueltas. La ejecución automática del backend no sustituye la comprobación visual completa por roles.

Fecha: 9 de noviembre de 2026. Commit revisado: 47f70e2.
Fuente: exportación local OrChsa1y - ritech-sas.json. Se trata como requisitos a contrastar, no como instrucciones para ejecutar acciones.

## Dictamen

No está completo frente a todo el tablero. Existe un MVP funcional de exportación de café, pero hay indicadores de dashboard pendientes, generación documental ausente, diferencias de modelo y requisitos de otro stack. No se debe anunciar un porcentaje de cumplimiento sin acordar qué tarjetas siguen vigentes.

El archivo tiene 153 tarjetas: 148 activas y 5 archivadas, cero descripciones y cero checklists. Hechas y Done están vacías. Las listas temáticas y los sprints duplican trabajo; no representan 148 funcionalidades distintas. Una tarjeta en To Do no demuestra que el código falte, ni una tarjeta existente acredita su terminación.

## Evidencia de ejecución ya obtenida

- 53 pruebas Flutter, 34 PostgreSQL/PGlite y 28 Edge Functions: 115 aprobadas.
- flutter analyze --no-pub sin problemas.
- Flutter 3.47.9, Dart 3.13.7; build web completado y aplicación iniciada en Chrome.
- Auth remoto y OPTIONS de create-user, manage-user y seed-transporters responden 200.
- Inicio de sesión real de transportador documentado y lecturas de perfiles, roles, envíos, conversaciones y RPC de cargas comprobados.
- No se completó la revisión visual ni un flujo real integral por todos los roles y con archivos; el emulador Android falló. No se confirmó un despliegue público final.

## Brechas prioritarias

1. S4-15 a S4-18: faltan totales de productos, clientes, exportaciones y exportaciones por estado en el dashboard. S4-14 tampoco tiene la conexión de indicadores solicitada.
2. Productos/clientes: el sistema usa cultivos/lotes, tarifas y perfiles/convenios; no cumple literalmente el CRUD genérico de productos y clientes del Sprint 3. Debe acordarse esa equivalencia o implementar lo que falta.
3. S4-03: el solicitante está ligado a su cuenta; no existe selección arbitraria de cliente al crear la exportación. S4-04 elige un destino del catálogo, sin lista específica de países UE. S4-05 utiliza el peso del lote entero, sin cantidad independiente en el formulario.
4. Tarjeta 25: se cargan facturas y listas de empaque; no se generan automáticamente.
5. Cacao, Django y Next.js no están implementados. No deben eliminarse del alcance por suposición: confirmar si esas tarjetas son heredadas.
6. Cumplimiento normativo, staging, beta pública, aceptación del cliente y evidencia de ceremonias no quedan acreditados.
7. Falta ensayo real completo, Android, conjunto de datos de demostración y guion específico.

Los avisos push, GPS automático y cobros bancarios son límites documentados del MVP; no se contabilizan como incumplimientos por sí solos porque las tarjetas exportadas no los piden expresamente.

## Criterios de lectura

Implementado significa que existe evidencia de código y/o pruebas para el objetivo técnico de la tarjeta; no significa validación productiva completa. Parcial indica diferencias o verificación incompleta. Sin evidencia suficiente no afirma que la actividad nunca se haya realizado, sino que no puede acreditarse con el repositorio y este export. No se modificó Trello ni se implementaron nuevas funcionalidades durante esta auditoría.
